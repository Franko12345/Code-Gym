# Code-Gym v0.1.0 — MVP Implementation Plan

> **For Hermes:** Use `feature-loop` (Matt Pocock) with 3-reviewer fanout
> per PR. Vertical slices ~50-150 LOC each. Squash-merge + delete branch.

## Goal

Ship a personal DSI training app for **OBI + maratona/olimpíada** with
a NeetCode-style grid, in-browser code editor, local sandbox execution,
email+password auth, and a curated roadmap seeded from OBI + NOIC +
CP-Algoritmos content.

## Architecture

- **Single FastAPI process** serves HTML + JSON, renders Jinja2
  templates, and exposes a small JSON API for the editor.
- **HTMX 2.x** drives navigation (no React/SPA). The **problem
  page** has non-HTMX JS for CodeMirror + localStorage autosave —
  documented as the one place where JS lives.
- **SQLite** for everything (users, problems, test cases,
  submissions). File at `data/code_gym.db`. WAL mode.
- **Local sandbox** runs user code in a child process with strict
  RLIMITs, **as a dedicated unprivileged `sandbox` user** (no shell,
  no home, no network) — privilege isolation, not just RLIMIT.
- **No judge-external calls** in v0.1.0. Pure local execution. Codeforces
  / AtCoder / LeetCode integration → v0.3.
- **No cron in v0.1.0.** Scrape scripts run on-demand via
  `python -m scripts.scrape.obi`. Cron / auto-update → v0.2.

## Data model (SQLite schema)

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,  -- bcrypt
    display_name TEXT NOT NULL,
    elo INTEGER DEFAULT 1000,
    created_at TEXT NOT NULL       -- ISO8601
);

CREATE TABLE topics (
    id INTEGER PRIMARY KEY,
    slug TEXT UNIQUE NOT NULL,     -- 'graphs', 'dp', 'arrays'
    name TEXT NOT NULL,            -- 'Grafos', 'Programação Dinâmica'
    obi_phase TEXT,                -- 'F1' | 'F2' | 'F3' | 'UNI' | NULL
    order_index INTEGER NOT NULL
);

CREATE TABLE problems (
    id INTEGER PRIMARY KEY,
    slug TEXT UNIQUE NOT NULL,
    title TEXT NOT NULL,
    topic_id INTEGER NOT NULL REFERENCES topics(id),
    difficulty INTEGER NOT NULL,   -- 1..5
    statement_md TEXT NOT NULL,
    input_format_md TEXT,
    output_format_md TEXT,
    examples_json TEXT,            -- [{"stdin": "...", "stdout": "...", "explanation": "..."}]
    source TEXT,                   -- 'OBI 2019 F1' | 'NOIC' | 'CP-Algos'
    source_url TEXT,
    created_at TEXT NOT NULL
);

CREATE TABLE test_cases (
    id INTEGER PRIMARY KEY,
    problem_id INTEGER NOT NULL REFERENCES problems(id),
    stdin TEXT NOT NULL,
    expected_stdout TEXT NOT NULL,
    is_sample INTEGER DEFAULT 0,
    weight INTEGER DEFAULT 1       -- for partial scoring
);

CREATE TABLE submissions (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    problem_id INTEGER NOT NULL REFERENCES problems(id),
    code TEXT NOT NULL,
    language TEXT NOT NULL,        -- 'cpp' | 'python'
    verdict TEXT NOT NULL,         -- 'AC' | 'WA' | 'TLE' | 'RE' | 'CE'
    runtime_ms INTEGER,
    memory_kb INTEGER,
    attempt_n INTEGER NOT NULL,    -- 1, 2, 3... per (user, problem)
    submitted_at TEXT NOT NULL
);

CREATE INDEX idx_submissions_user_problem
    ON submissions(user_id, problem_id);

-- v0.2 (schema present but unused in MVP)
CREATE TABLE review_schedule (
    user_id INTEGER NOT NULL REFERENCES users(id),
    problem_id INTEGER NOT NULL REFERENCES problems(id),
    due_at TEXT NOT NULL,
    interval_days INTEGER NOT NULL,
    ease_factor REAL NOT NULL,
    PRIMARY KEY (user_id, problem_id)
);
```

## Tickets (15 total, 4 milestones)

> Format: **M{n}.T{k} — title** — short description

### Milestone 1 — Auth (4 tickets)

- **M1.T1 — schema users + bcrypt hash util** — `db.py` creates `users`
  table on startup, `app/auth/passwords.py` has `hash(plain) -> str` and
  `verify(plain, hashed) -> bool` with bcrypt cost=12.
- **M1.T2 — JWT encode/decode + cookie middleware** — `jwt_utils.py`
  with HS256, secret from env, 30-day expiry. Middleware reads
  `cg_session` cookie, attaches `request.state.user`.
- **M1.T3 — `app/cli.py create-user`** — `python -m app.cli create-user
  email@x.com senha123 "Nome"`. No public signup route. Invite-only.
- **M1.T4 — login/logout routes + login.html** — `POST /login` verifies
  bcrypt, sets JWT cookie, redirects to `/roadmap`. `POST /logout`
  clears cookie. No "forgot password" in MVP.

### Milestone 2 — Content (3 tickets)

- **M2.T1 — schema problems + test_cases + seed loader** — `db.py`
  migrations create tables, `scripts/seed.py` loads YAML from
  `data/seed/` into DB.
- **M2.T2 — `scripts/scrape/obi.py`** — fetches OBI past problems
  (statement + sample input/output) from public sources, writes
  `data/snapshots/obi-YYYY-MM-DD.yaml`. Manual run.
- **M2.T3 — `scripts/scrape/noic.py`** — same shape for NOIC content.
  Idempotent (same input → same output, no duplicates).

### Milestone 3 — Navigation (3 tickets)

- **M3.T1 — `base.html` + dark theme CSS + sidebar** — single CSS file
  with NeetCode-inspired dark palette (`#0d1117` background, `#161b22`
  cards, `#3fb950` green for solved). Sidebar links: Roadmap, Problems,
  Profile, Logout.
- **M3.T2 — `/roadmap` route + NeetCode-style topic grid** — list topics
  in OBI F1 order, each shows progress bar (solved/total) and a sample
  of unsolved problems.
- **M3.T3 — `/u/{username}` profile + grid of solved/unsolved** — public
  profile with grid of all problems the user has attempted, colored by
  status (green=AC, red=WA, yellow=attempted, gray=untouched).

### Milestone 4 — Editor + Sandbox + Submission (5 tickets)

- **M4.T1 — `sandbox/languages.py`** — `compile_cpp(source) -> (cmd, args)`
  and `run_python(source) -> (cmd, args)` returning argv lists. No
  network access (`-static-libstdc++` for C++ if available, else just
  flags).
- **M4.T2 — `sandbox/runner.py` UID-isolated** — `run(code, lang,
  test_case) -> Verdict` runs subprocess with:
  - `preexec_fn=setpgrp()` + `preexec_fn=os.setuid(sandbox_uid)`
  - `RLIMIT_CPU=2`, `RLIMIT_AS=256MB`, `RLIMIT_NPROC=1`,
    `RLIMIT_FSIZE=1MB` (no writing outside `/tmp/sandbox-<uuid>/`)
  - `timeout=2.5s` hard kill
  - Drop-in `nogroup` group, no shell binary in PATH
  - Returns `(verdict, runtime_ms, stderr_excerpt)`
- **M4.T3 — `sandbox/limits.py` + `sandbox` user provision script** —
  `deploy/setup-sandbox-user.sh` creates system user `sandbox` with
  `/bin/false` shell, no home, locked password. Idempotent.
- **M4.T4 — `POST /problems/{slug}/submit`** — accepts `{code, language}`,
  runs against all test cases in `asyncio.to_thread`, aggregates
  verdict (AC if all pass, else first failure), saves to `submissions`,
  updates user ELO, returns JSON for HTMX swap.
- **M4.T5 — `/problems/{slug}` page + CodeMirror editor** — problem
  statement on left, editor on right (CodeMirror 6, mode = language),
  "Run sample" + "Submit" buttons. localStorage autosave on
  `keyup` debounced 500ms.

## Test plan

Per ticket, pytest first. Critical coverage:

- `test_auth.py`: bcrypt roundtrip, JWT roundtrip, middleware sets
  `request.state.user`, login route sets cookie, logout clears it.
- `test_sandbox.py`:
  - AC: code matches expected output → verdict AC
  - WA: code prints "42" for expected "43" → verdict WA
  - TLE: `while True: pass` → verdict TLE within 3s
  - OOM: allocate 512MB → verdict RE within 3s, no host OOM
  - Forbidden: `import os; os.system('rm -rf /')` → verdict RE, host intact
- `test_problems.py`: seed loader is idempotent, slug collisions raise.
- `test_roadmap.py`: next-problem returns harder problem from current topic.
- `test_profile.py`: grid rendering matches solved/unsolved counts.

## Sandbox safety: the key fix from review

The single biggest risk reduction in this plan. The sandbox **must**:

1. Run as a dedicated **unprivileged system user** (`sandbox`), created
   by `deploy/setup-sandbox-user.sh`:
   ```bash
   useradd --system --shell /usr/sbin/nologin --no-create-home \
           --uid 32768 sandbox
   ```
2. FastAPI runs as `hermes` (not root). The sandbox runner does:
   ```python
   pwd = pwdb.getpwnam("sandbox")
   preexec_fn = lambda: (
       os.setgroups([pwd.pw_gid]),
       os.setuid(pwd.pw_uid),
       resource.setrlimit(resource.RLIMIT_CPU, (2, 2)),
       resource.setrlimit(resource.RLIMIT_AS, 256 * 1024 * 1024, 256 * 1024 * 1024),
       resource.setrlimit(resource.RLIMIT_NPROC, (1, 1)),
       resource.setrlimit(resource.RLIMIT_FSIZE, (1 * 1024 * 1024, 1 * 1024 * 1024)),
   )
   subprocess.run(argv, stdin=PIPE, stdout=PIPE, stderr=PIPE,
                  timeout=2.5, preexec_fn=preexec_fn, check=False)
   ```
3. Working dir is a fresh `tmpfs`-backed `/tmp/sandbox-<uuid>/` wiped
   after run.
4. No network namespace setup in MVP (single-user trust boundary).
   If we ever open to public users → add `network_unshare()`.

This is more than the original "RLIMIT only" plan. It uses OS-level
isolation (UID/GID), not just libc limits. A `g++` compiler bug that
escapes RLIMIT still hits a uid with no shell, no home, no write
access to your `/home/hermes`.

## Risks & trade-offs

| Risk | Likelihood | Mitigation |
|---|---|---|
| Sandbox escape via compiler bug | Very low | UID isolation, no shell, rlimits |
| Code-Gym grows into LeetCode-clone | Medium | YAGNI per ticket; review fanout catches |
| OBI scrape source changes | Medium | Scraper is best-effort, manual rerun |
| Multi-user without invite-only | Now blocked | CLI-only account creation |
| 5 langs in MVP → sandbox complexity | Now blocked | C++ + Python only |
| HTMX + CodeMirror boundary unclear | Low | Documented in ADR-0001 |
| Cron for scraping is overkill | Now blocked | Manual runs only in MVP |

## How to verify the whole MVP

After all 15 tickets merged:

```bash
# 1. Provision sandbox user (once)
sudo deploy/setup-sandbox-user.sh

# 2. Seed DB
python -m scripts.seed --file data/seed/topics.yaml
python -m scripts.seed --file data/seed/obi_problems.yaml
python -m scripts.seed --file data/seed/noic_problems.yaml

# 3. Create first user
python -m app.cli create-user franco@froto.online 'senha' 'Franco'

# 4. Run app (dev)
docker compose up

# 5. Smoke flow
curl -L https://code-gym.froto.online           # redirects to login
# Login → /roadmap shows F1 topics
# Click topic → grid of problems
# Click problem → editor + submit
# Submit C++ "hello world" → AC on first sample

# 6. Run tests
pytest tests/ -v

# 7. Deploy (prod)
sudo cp deploy/code-gym.service /etc/systemd/system/
sudo systemctl enable --now code-gym
```

## Workflow

1. Each ticket = 1 PR via `feature-loop-single-actor` (no reviewer repo).
2. Branch per ticket: `m1-t1-bcrypt-util`, `m1-t2-jwt-cookie`, ...
3. Squash-merge + delete branch on approval.
4. 3-reviewer fanout per PR (ponytail + discipline + correctness).
5. After M1-M4 complete, tag `v0.1.0`, write release notes.
